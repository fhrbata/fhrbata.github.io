The problem (IDF-15485)

  • Every ESP-IDF component carries three hand-written configuration files, each in its own Domain-Specific Language (DSL)
  • CMakeLists.txt — CMake DSL, imperative (describes how, step by step)
  • idf_component.yml — YAML manifest, declarative (describes what you want, not how to get there)
  • Kconfig / Kconfig.projbuild — Kconfig DSL, for build and compile-time configuration
  • Three syntaxes, three responsibilities, all describing the same component

Three files, three languages


# CMakeLists.txt
idf_component_register(
    SRCS "data_logger.c"
         "logger_uart.c"
    INCLUDE_DIRS "include"
    REQUIRES log
    PRIV_REQUIRES esp_timer)
            

# idf_component.yml
version: "1.0.0"
description: "Data logger"
dependencies:
  idf: ">=5.3"
  espressif/cmp: "^3.3.3"
            

# Kconfig
menu "data_logger"
    config DATA_LOGGER_ENABLE
        bool "Enable data logger"
        default y
    config DATA_LOGGER_BUFFER_SIZE
        int "Buffer size"
        default 1024
        range 128 8192
endmenu

What hurts

  • Onboarding — new developers must learn three DSLs to publish their first component
  • IDE support — CMake is not IDE-friendly: hard for tools like CLion, VS Code, or Eclipse to parse and modify reliably
  • Declarative vs imperative gap — idf_component.yml and CMakeLists.txt both describe "what the component is", but in two different paradigms

What components actually do

  • Most components use only a small subset of CMake features
  • List source files
  • Declare include directories
  • Specify component dependencies
  • Maybe embed a file or two
  • A declarative YAML schema can cover this fully
  • For the common case, all of the above can be expressed in idf_component.yml alone

The vision

  • One YAML manifest per component — idf_component.yml
  • CMakeLists.txt shrinks to a one-line stub: 
    
idf_component_register_from_manifest()
  • Kconfig fully expressible inside the same YAML
  • Schema-validated, IDE-friendly, human-readable
  • Additive: existing components keep working unchanged; the manifest opt-in covers the common case

End goal: component defined purely in YAML

The register: section

  • Each idf_component_register(...) argument maps 1:1 to a YAML key (snake_case)
  • sources, src_dirs, exclude_srcs
  • include_dirs, priv_include_dirs
  • embed_files, embed_txtfiles
  • ldfragments, required_idf_targets
  • whole_archive (boolean flag)
  • Two more sub-keys: kconfig: and kconfig_projbuild:

Kconfig in YAML

  • Grammar covers every construct esp-idf-kconfig supports
  • Entry kinds: config, menuconfig, choice, menu, if/then, comment
  • Sources: source, rsource, osource, orsource
  • Types: bool, int, hex, string
  • Polymorphic attributes (scalar or list-of-clauses with optional if): prompt, default, range, select, imply
  • depends_on: scalar or list (no if tail; Kconfig forbids it)
  • visible_if: only on menu (the only place Kconfig accepts it)

Kconfig example: simple config & menuconfig


# Master switch.
- config: DATA_LOGGER_ENABLE
  type: bool
  prompt: "Enable data logger"
  default: y
  help: |
    When enabled, the data logger captures sensor values to a
    circular in-memory buffer.

# menuconfig: nested options, body auto-wrapped in `if`.
- menuconfig: DATA_LOGGER_DEBUG
  type: bool
  prompt: "Debug options"
  default: n
  depends_on: "DATA_LOGGER_ENABLE"
  body:
    - config: DATA_LOGGER_DEBUG_VERBOSE
      type: bool
      prompt: "Verbose debug output"

Kconfig example: polymorphic default / range


# int with list-form default and range, target-aware.
- config: DATA_LOGGER_BUFFER_SIZE
  type: int
  prompt: "Buffer size (bytes)"
  default:
    - default: 4096
      if: "IDF_TARGET_LINUX"
    - default: 1024
  range:
    - range: [256, 65536]
      if: "IDF_TARGET_LINUX"
    - range: [128, 8192]

# choice: pick exactly one backend.
- choice: DATA_LOGGER_BACKEND
  prompt: "Logger backend"
  default: DATA_LOGGER_BACKEND_UART
  options:
    - config: DATA_LOGGER_BACKEND_UART
      type: bool
      prompt: "UART"
    - config: DATA_LOGGER_BACKEND_FILE
      type: bool
      prompt: "File on SPI flash"

Kconfig example: if/then, comment, rsource


# if/then block: visible only when the network backend is selected.
- if: "DATA_LOGGER_BACKEND_NETWORK"
  then:
    - config: DATA_LOGGER_NET_HOST
      type: string
      prompt: "Server hostname"
      default: "127.0.0.1"
    - config: DATA_LOGGER_NET_TLS
      type: bool
      prompt: "Use TLS"
      default: n
      select: MBEDTLS_CERTIFICATE_BUNDLE

# Conditional comment.
- comment: "Network backend selected; configure server settings above."
  if: "DATA_LOGGER_BACKEND_NETWORK"

# Pull in an existing hand-written Kconfig fragment, relative to component.
- rsource: "Kconfig.platform"

Dependencies — registry, local, plain component

The same dependencies: block carries everything; the value tells the manager which:

FormExisting manager termMeaning
foo: "^1.0"ESP Component Registry dependency (auto-prefixed)Bare name + version → auto-prefixed to espressif/foo, fetched from registry
ns/foo: "^1.0"ESP Component Registry dependencyNamespaced + version → fetched from registry as ns/foo
foo: { path: ../path }Local Directory dependencyMount a local directory
foo: { git: <url>, version: <ref> }Git dependencyClone a git repo
foo: (no value)Component dependency (new)Look up foo in the build system's already-discovered components. No fetch, no version solve. Errors on no match.

The plain component-dependency form is what lets local + built-in IDF deps live alongside registry deps in one block.

Two implementations

Same user-visible feature, two architectures. Both ship as drafts; the talk is to pick one.

Approach 1: build-system-driven

  • esp-idf !48143
  • ~1500-line tools/cmakev2/manifestgen.py
  • esp-idf side generates CMake and Kconfig artifacts
  • Component manager unchanged
  • Works with IDF_COMPONENT_MANAGER=0

Approach 2: manager-driven

  • esp-idf !48540
  • idf-component-manager !641
  • Generator moves into the manager
  • esp-idf side: stub + Kconfig wire-up only
  • Adds plain component dependencies in dependencies:

Single owner for idf_component.yml semantics no (manager owns deps, build system owns register:) yes
register.requires: / register.priv_requires: in schema not in schema — deps unified under dependencies:

Approach 2: plain component dependency flow

  1. Build system writes local_components_list.temp.yml with every discovered component (name, path, source category)
  2. Manager loads the manifest; sees log: with no value
  3. Looks log up in the discovered list — finds it as idf_components
  4. Rewrites the entry in-memory to DependencyItem(path=<log's path>)
  5. The synthetic path: dep flows through LocalSource: no version solve, no download
  6. Post-resolution dedup keeps log registered as idf_components (no reclassification)
  7. inject_requirements emits MANAGED_PRIV_REQUIRES "log"; v2 shim wires it into the parent's PRIV_REQUIRES
  8. No match → fatal error with the list of available local components (typos surface early)

Shared semantics (both approaches)

  • Stub-mode requirement: if register: declares any idf_component_register-arg key (or, in Approach 2, dependencies: carries a plain component dependency), CMakeLists.txt must be the one-line stub — no clash with a hand-written idf_component_register(...)
  • Conflict matrix: register.kconfig: vs source-tree Kconfig, register.kconfig_projbuild: vs source-tree Kconfig.projbuild — errors
  • Error reporting: every diagnostic carries idf_component.yml:LINE; generated Kconfig has source-comment markers (# idf_component.yml: register.kconfig[2].config.FOO) so kconfgen errors trace back
  • Backward compat: components without a register: section continue to work exactly as today
