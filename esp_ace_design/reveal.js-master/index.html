ESP-ACE

dispatcher, configuration, emitter,
workspaces and profiles

Frantisek Hrbata — September 2026
What is merged into master, and why it is built this way. Stop me anywhere - the point is to discuss the ideas, not to announce them.

What this covers

  • dispatcher — one Def per command, and everything computed from it
  • configuration — scopes, and every key declared in code, with a type
  • emitter — the command uses one interface. The command line options decide where the output goes.
  • logger — slog goes through the same emitter
  • workspaces — one configured build, with a name
  • profiles — what a workspace is made from
Six areas. They are not independent - the dispatcher's Def is what the configuration, the completion and the manual all read.

dispatcher

Like git, but written by us

  • ace <verb> <subverb>, options inherited down the tree, ace-<verb> on PATH — the same form people know from git
  • no cobra. It was there at the start and was taken out
  • what we need and cobra does not give:
    • one declaration that also defines config keys, environment variables and events
    • allowed values written once, on the option: the parser checks them, completion offers them, the help lists them
    • a model package that imports only the standard library
    • a mistake in a command definition is found at startup, not by a user
cobra came with the first scaffold (856b75a7). We used it, then removed it on purpose, in one commit: "dispatch through the in-house parser, drop cobra" (8af3113c). If somebody says cobra completes values: it does, with RegisterFlagCompletionFunc and ValidArgsFunction, registered apart from the flag. What cobra has no place for is the list of allowed values. pflag has no such field, so the check, the completion and the help are three pieces of code. In ace all three read Choices on the row: Opt.Set checks it, completion offers it, and the help card prints "(human | json | ndjson)".

One Def is the whole command


type Def struct {
    Name     string
    Summary  string
    Doc      Doc
    ...
    Needs    []Need
    Opts     []Opt
    Configs  []ConfigDef
    Envs     []EnvDef
    Events   []EventDef
    Controls []ControlDef
    Args     []Arg
    Validate func(d *Def, args []string) error
    Complete func(d *Def, args []string, toComplete string) []Candidate
    Run      func(c Ctx) error
    Subs     []*Def
}
  • the word typed on the command line
  • the one line shown in the parent's help and in completion
  • the manual, printed by --help and ace help. -h prints a short card.
  • what must be true before it runs
  • flags, with type, default and allowed values
  • the config keys this command defines
  • the environment variables it reads
  • events it may send while working
  • requests a connected program may send it
  • positional arguments, each with its own completion
  • a check of the arguments, after parsing
  • extra names for the subcommand position. The root offers ace-<verb> programs this way.
  • the function that runs the command
  • its subcommands. ace config does no work itself; it only groups the commands below it.
Everything a user can see or set is in one struct literal. No init() that registers a flag somewhere else, no second place a config key can be defined. The struct is internal/command/command.go:783-925. The "..." hides five fields: Parent (Init sets it), Hidden (not listed, like git's plumbing commands; ace idf is hidden), Passthrough (the rest of the line goes to another program), OwnsStdout and HumanDefault (what stdout holds). No command defines an environment variable today. The size example on the next slide shows how one would.

The tree is fixed, and every part reads it


var aceCmd = cmd.Def{
    Name:    "ace",
    ...
    Subs: []*cmd.Def{
        helpCmd,
        buildCmd,
        completionCmd,
        configCmd,
        idfCmd,
        initCmd,
        profileCmd,
        statusCmd,
        switchCmd,

        workspaceCmd,
    },
}

func dispatch() int {
    ...
    cmd.Init(&aceCmd)
    ...
}
  • the whole command tree is written in code, one Def per command. The root has 11 subcommands; idf is hidden.
  • the tree is built here, once, when the program starts. Init sets every parent link and checks the whole tree.
  • a duplicate config key, a documentation reference to a name that does not exist, an option bound to the wrong type — ace panics here. A wrong definition never reaches a user.
  • after this the tree does not change. The parser, completion, the configuration registry, the help card and --help --format json all read the same tree.
  • internal/command imports only the standard library, so the config package can read the tree with no import cycle
cmd/ace/main.go:75 is the root, main.go:323-335 its subcommands, and main.go:824 the Init call, the first step of dispatch(). The standard-library-only rule is what makes the rest possible. The model must not know what a config store or an emitter is, or nothing else could import it. Spend time on bullet three. These are not runtime errors. The tree is written in code and compiled into the binary, so a mistake in it is a programming error and ace refuses to start.

One run, step by step


// cmd/ace/main.go, dispatch()
cmd.Init(&aceCmd)
call, err := cli.Parse(&aceCmd, os.Args[1:])
if err = call.ApplyEnv(); !decided { ... }
projectRoot, err = findProject()
if err = config.Init(&aceCmd, projectRoot, ...); !decided { ... }
if err = call.ApplyConfig(config.Get()); !decided { ... }
code, err, dispatched := call.RunExternal()
f.add(ide.InitEmitter(setup))
slog.SetDefault(slog.New(ide.LogEvents(logLevel)))
f.add(emitter.Started())
if err := f.first(); err != nil { ... }
if (flagHelpShort || flagHelpLong) && !call.Completing() { ... }
if flagVersion && !call.Completing() { ... }
if call.Complete() { ... }
ctx, stop := process.SignalContext()
release, err := checkNeeds(ctx, emitter, call.Cmd())
return emitter.Finished(call.Run(ctx, projectRoot))
  • the tree is built and checked
  • the words are matched to the tree. A wrong line is a usage error: exit code 2.
  • the parser sets the flags. Environment variables fill the options still unset. Then the project is found, the configuration is read, and it fills the rest.
  • a verb that is not built in runs an ace-<verb> program from PATH, if core.allow-pathcmds allows it
  • the emitter is chosen, the logger goes through it, and the run starts
  • an error from any step above is printed only now, in the chosen format. ace --format json bogus prints a JSON error.
  • -h, --help, --version and TAB answer here and stop. The needs are not checked yet, so help works with no ESP-IDF.
  • Ctrl-C handling starts, the needs are checked, and the command runs. Finished returns the exit code.
cmd/ace/main.go:810-1062. Every line on the left is a real line of dispatch(), in order; the bodies are cut to "...". Every step runs even after an error. The error is recorded with f.add and printed at f.first, once the format is known (the comment at main.go:826). That is why --format json also applies to a usage error: ace --format json bogus prints the JSON envelope with exit code 2. The gates for -h, --help, --version and TAB come before checkNeeds on purpose (main.go:1049): a card, a version and a TAB work on a machine with no ESP-IDF. Signal handling starts after the gates (main.go:1038), so a Ctrl-C during help ends ace at once.

Options are inherited down the tree


$ ace build -v                       # watch the compiler output
$ ace build --format json            # machine output from a build

$ ace workspace list --format json   # two levels deep
$ ace config get core.log-level --format json

$ ace --format json workspace list   # before the verb, same result
			

$ ace workspace list -h
usage: ace workspace list [<options>]

Options inherited from ace
    ...
    --format <format>     output rendering (human | json | ndjson)
    -h                    show the help card
    --help                show the full manual
    ...
  • a root option works after the leaf command, where you would naturally type it
  • at any depth. workspace list and config get are two levels down and still accept it.
  • before the verb also works. The same option, the same result.
  • --format is declared once, on the root Def. No command repeats it.
  • the help card names the command each inherited option came from. ace workspace list declares none of its own, so its card is all inherited.
Cobra has persistent flags, so this is not new. What is different is that the help card can say which command an inherited option came from, without anyone writing that down: the parent link is in the tree, so the card reads it. The -v example is the one people use every day. You want the compiler output, and -v is declared on the root, but you type it where the command is. The card is real and cut: it has eleven inherited options, and the three shown are consecutive.

A command declares what it needs


// cmd/ace/build.go
Needs: []cmd.Need{
    cmd.NeedIDF,
    cmd.NeedWorkspaceLocked,
},

NeedIDF              an activated ESP-IDF
NeedIDFProject       a project at or above here
NeedWorkspace        a workspace whose tree matches
NeedWorkspaceLocked  a workspace, held for the run
NeedBuild            a workspace, built first
NeedBuildLocked      built, and held for the run
  • a list of what must be true before the command function runs. The dispatcher checks it first, so a command never starts work it cannot finish.
  • an ESP-IDF, a project, a workspace: each is found once, by the dispatcher, not by every command
  • the lock is declared, not a call you can forget
  • ace target monitor declares NeedBuild: the workspace is built before the console opens. It is held only during the build, so you can build again while the monitor runs.
  • the checks run in the listed order, and the first one that fails stops the run. ace build lists NeedIDF first: without ESP-IDF nothing can be built, whatever state the workspace is in.
This is what keeps command functions short. Most of what a command would otherwise do first - find the project, find the workspace, take the lock, check the tree - is a list of constants here. The constants and their comments: internal/command/command.go:681-731. The checks: checkNeeds, cmd/ace/main.go:557-601. NeedBuild gives the workspace back after the build at main.go:595. The reason for the order is the comment at build.go:45-47. (The comment on Need says the values are unordered, but checkNeeds walks the list in order.)

The dispatcher hands over a context


type Context struct {
    context.Context   // cancellation

    Cmd  *cmd.Def     // this command
    Args []string     // its arguments

    ProjectRoot string
    Cfg     *config.Config
    Emitter ide.Emitter
    Log     *slog.Logger

    Peer *ide.Peer    // nil unless --rpc
}
  • when the run is cancelled this reaches exec.CommandContext and anything else that takes a context
  • the Def of the command that is running
  • the positional arguments for the command to handle
  • the project directory, or empty when there is no project
  • the configuration, already read from every scope and checked
  • where output goes
  • the run's logger
  • the connected program, when the command was started with --rpc. That option is not global: only a command that supports it declares it. Today that is ace target monitor.

the command only has to do its own work

Peer is a field on purpose, not a global. A command that serves requests receives the connection. A command that did not receive one cannot find one.

func completeWorkspaces(*cmd.Def, []string, string) []cmd.Candidate {
    if projectRoot == "" {
        return []cmd.Candidate{}
    }
    s, err := workspace.Read(projectRoot)
    if err != nil {
        return []cmd.Candidate{}
    }
    names := s.Names()
    out := make([]cmd.Candidate, 0, len(names))
    for _, name := range names {
        out = append(out, cmd.Candidate{Name: name})
    }
    return out
}

// ace <TAB>, on the root command
Complete: func(d *cmd.Def, _ []string, w string) []cmd.Candidate {
    ... // adds the ace-<verb> programs found on PATH
}

  • Complete on an option: a function that returns the candidates for that option's value
  • Complete on a positional argument: the same function type
  • a real one, from cmd/ace/switch.go: it reads the workspace file and returns the names. A candidate can also carry a help text.
  • Complete on a command with subcommands: extra names for the subcommand position. The root uses it to offer ace-<verb> programs from PATH, when core.allow-pathcmds is on.
  • the shell script only sends the words and the cursor position to ace __complete, and prints what comes back. One backend; small scripts for bash, zsh, fish and powershell.

Signals: the first one asks, the second one kills


// internal/process/signal.go
for s := range sig {
    switch {
    case foreground.Load() > 0:
    case !cancelled:
        cancel(fmt.Errorf("%w: %s", ErrSignal, s))
        cancelled = true
    default:
        killTracked()
    }
}

// internal/process/group_unix.go
func stop(p *os.Process, sig syscall.Signal) error {
    return syscall.Kill(-p.Pid, sig)
}
  • the first Ctrl-C (or SIGTERM, or SIGHUP) cancels the run's Go context. The cause records which signal it was.
  • every child started through internal/process then gets SIGINT, sent to its whole process group. Children run in their own group, so the terminal's Ctrl-C reaches ace alone, and ace passes it on: to ninja, and to the compilers under it.
  • the second Ctrl-C kills every child still running, SIGKILL to the group, and closes its pipes so ace stops reading at once
  • while a child uses the terminal (Console mode, meant for gdb) ace ignores signals: there, Ctrl-C must reach gdb and stop the program it debugs. Built; no command uses it yet.
  • ace itself is never killed by this. It waits for the children and ends the run normally. signal.NotifyContext is not used, because it delivers only the first signal.
  • exit codes 130 and 143 exist and the cause says which signal, but nothing connects them yet. Measured today: a build interrupted with Ctrl-C exits with 3.
Verified in code and by test. The loop is internal/process/signal.go lines 53 to 62. The AfterFunc that sends SIGINT to a child's group on cancel is proc.go:118-123; killTracked is proc.go:222; Setpgid is group_unix.go:18. On Windows only os.Interrupt is delivered. The test: ace build in a scratch project, SIGINT after six seconds. ninja printed "build stopped: interrupted by user", no ninja or compiler was left, ace printed "ERROR: cmake could not build ...: signal: interrupt" and exited with 3. The exit code gap: ExitInterrupted and ExitTerminated are defined in internal/fault/exit.go:31-32, ErrSignal carries the signal, but nothing calls context.Cause on the run's context. fault.ExitCode returns the code the error carries, and the build's error carries 3.

Two ace runs on one workspace


$ ace build &                    # in one terminal
$ ace status                     # in another
...
tree              ready
held by           ace build, pid 6224, for 2 seconds

$ ace build
ERROR: workspace 'dev' is busy: ace build (pid 6224 on espressif)
       has been running for 5s
$ echo $?
7

$ ace init dev esp32c6           # the same answer
$ ace workspace remove dev       # the same answer
  • build, init and workspace remove claim the workspace for the whole run. The claim is a record in .ace/workspaces.yaml: command, pid, host, since. status shows it.
  • a second run that needs the same workspace is refused at once, with exit code 7. It does not wait for the first one: you would sit in front of a silent command, and your build would only start when the other one ends.
  • commands that only read (status, workspace list, config get) run at any time. The record file is written under a short lock, and every write is atomic: a crash cannot leave half a file.
  • a claim whose process is gone (same host, no such pid) is taken over, so a killed run does not block the workspace forever
  • idf.py takes no lock (tools/idf.py and idf_py_actions: none), and neither do cmake or ninja. Two runs in one build tree overwrite each other's files.
All output is real: a full rebuild in the background, then the three commands. ace build takes the claim through NeedWorkspaceLocked (workspace.Hold, internal/workspace/store.go:309). ace init and ace workspace remove take it with Store.Claim (store.go:291), in the same edit that changes the record. The refusal is exit 7, ExitConflict. The short lock around the record file is atomicio.Acquire with a two-second wait (store.go:32); it is never held while cmake or ninja runs. A claim whose process is gone (same host, no such pid) is dropped when the record is read: workspace.Read, store.go:103-105, and Holder.gone, store.go:350. For idf.py I searched tools/idf.py and tools/idf_py_actions for flock, lockf, filelock and portalocker: nothing.

configuration

Scopes

The same idea as git config: several files, and the closest one wins.

scopewhere it lives
built-inthe defaults in the command definitions
system$ACE_HOME/config.yaml
user<user config dir>/ace/config.yaml
project<project>/.aceconfig.yaml
workspace<project>/.ace/workspaces/<name>/config.yaml
filethe file --config names. For one run it replaces system, user, project and workspace.
commandthe -c key=value options

a higher scope replaces a lower one completely. A list key is different: it collects the values from every scope.

Lowest first. Seven scopes; git has fewer, and --config is not the same as git config --file: --config replaces four scopes for one run, --file edits one file. The four: internal/config/load.go:101-112 returns right after reading the --config file, so system, user, project and workspace are not read. ace's own --config help still says three scopes.

The files are YAML


# .aceconfig.yaml            (project scope)
init:
  target: esp32c3
core:
  profiles:
    - ./team-profiles

# .ace/workspaces/dev/config.yaml  (workspace scope)
core:
  log-level: debug
  • a key is its path in the YAML tree: init.target is target under init
  • a list key is a YAML list
  • each workspace has a file of its own. ace config set writes there unless --scope says otherwise.
  • a value is kept as the text written in the file. The key's type parses it, not YAML. So no stays the word no, and 0x10000 stays hex.
  • a key with no value (key:, ~, null) is an error. To say nothing, do not write the key.
Both files are real, from the demo project. The text rule is in internal/config/config.go, in the package comment: YAML's own typing is not used, on purpose, so quoting never changes a value's meaning.

an included file is checked by the rules of the scope that includes it, so a project cannot turn on core.allow-pathcmds through an include. A file that includes itself, directly or through another file, is refused.

emitter

One interface. The dispatcher picks the real one.


type Emitter interface {
    Started() error
    Result(data any, human func(w io.Writer))
    Event(ev Event, human func(w io.Writer))
    Diagnostic(d Diagnostic)
    log(rec slog.Record)
    Finished(err error) int
}
  • opens the run, and fails if there is nowhere to send the output
  • the result: the data for a machine and the text for a person
  • something that happened during the run, under a name the command declared
  • one problem the user can fix, printed the same way by every command
  • a log line. It is not exported: a command logs with log/slog, and only the emitter prints the line.
  • closes the run and returns the exit code

a command uses an Emitter and knows nothing else. The dispatcher reads --format, -q, whether stdout is a terminal, and --rpc where the command declares it, and gives the command the one that matches.

internal/ide/emitter.go:93-149. Result and Event look alike and do different things: a result is stored and printed once at the end, and there is one per run. An event is printed as soon as it happens, and there can be any number. log is lower case on purpose (emitter.go:126-141): nothing outside internal/ide can call it, so a command cannot print a log line in a style of its own.

Exit codes


// internal/fault/exit.go
const (
    ExitOK          = 0   // complete success
    ExitInternal    = 1   // unexpected fault: a bug
    ExitUsage       = 2   // bad flags, arguments, or subcommand
    ExitUser        = 3   // valid usage, a fixable precondition unmet
    ExitNotFound    = 4   // a required resource or device is not there
    ExitPermission  = 5   // access denied
    ExitEnvironment = 6   // toolchain or environment not set up
    ExitConflict    = 7   // conflicts with the current state
    ExitNoData      = 8   // the query ran and has no answer
    ExitTimeout     = 124 // the operation exceeded its deadline
    ExitInterrupted = 130 // cancelled by SIGINT (128 + signal)
    ExitTerminated  = 143 // cancelled by SIGTERM (128 + signal)
)
			

$ ace --format json switch nope
{
  ...
  "status": "error",
  "exit_code": 3,
  ...
  "error": {
    "category": "user",
    "message": "no such workspace: nope (this project has dev, prod)",
    "exit_code": 3
  }
}
  • each code means one thing, and the numbers do not change. A script knows what happened from the code alone.
  • 2: the command line is wrong, for example ace --bogus status
  • 3: the line is right, but something you can fix is missing, for example ace switch nope
  • 6: ace build when no ESP-IDF is activated
  • 7: a second ace build on a busy workspace
  • 8 is not a failure: the query ran and found nothing, for example ace config get of a key that no scope sets
  • 130 and 143 are defined, but not used yet. A build stopped with Ctrl-C ends with 3.
  • the JSON result has the code and a category: usage, user, environment, internal, cancelled or timeout
The table is internal/fault/exit.go:20-33 and its comment says why: a caller recovers what kind of outcome it was from the status alone, with no message to parse, so each code means one thing and the numbers never move. Every example is measured: ace --bogus status gave 2, ace switch nope gave 3, ace build with no IDF_PATH gave 6 ("IDF_PATH is not set: run . <esp-idf>/export.sh first"), a busy workspace gave 7, and ace config get of an unset key gave 8 and printed nothing. 8 is like grep's 1, "nothing matched". ace cannot use 1 for it, because 1 means a bug in ace. The categories are fault.Category, exit.go:37-44. 130 and 143 exist, but nothing maps a signal to them yet; see the signals slide.

A workspace is one configured build


version: 1
current: dev
workspaces:
  dev:
    binding:
      target: esp32c6
      build-dir: build-dev
      sdkconfig: sdkconfig.dev
      generator: Ninja
      idf-path: ~/esp-idf

.ace/workspaces.yaml

  • one file per project, and the name of the current workspace
  • the binding: every value passed to cmake, decided once. It holds the final values, not what you typed, and which ESP-IDF configured it.
  • when it was created and when it was last configured
  • to change the binding you run ace init again. The build tree is cleared, because cmake keeps the generator, the source dir and every define until its cache is gone. The sdkconfig is moved to sdkconfig.dev.old, and the workspace's own settings are written again from the profile.
I say "decided when it is created" and not "immutable". You can change the binding, but only by running init again, and that clears the build tree. cmake cannot change those values in place. Measured: ace init dev esp32c6 on an existing dev printed "WARNING: ESP-ACE-0001: sdkconfig.dev starts again from its defaults ... kept as sdkconfig.dev.old", and a value set with ace config set in that workspace was gone. Code: runInit, cmd/ace/init.go:425-468, and workspace.Create, internal/workspace/create.go:96-127.

a command line names one profile. To combine profiles, one extends another. An option on the line still wins over any profile: ace init tt ci -t esp32s3 builds for esp32s3.

Real output. The rules are in ace profile --help, in the sections "Using another profile" and "Precedence": an option on the command line overrides the profile, and the profile overrides the configuration files. A later name in profile.extends wins over an earlier one. profile.description and profile.type are not inherited. Measured: ace init w esp32c6 ci fails with "too many arguments" (exit 2), and ace init tt ci -t esp32s3 printed "tt: esp32s3 in build-tt". An extends loop is refused: "profile.extends: "a" reads its way back to itself". A missing name: the error lists every directory searched.

Where a profile name is looked for


system      $ACE_HOME/profiles/
            + what the system's core.profiles names
user        <user config dir>/ace/profiles/
            + what the user's core.profiles names

            + what the project's core.profiles names

built-in    the chips, the boards and default
  • each scope has a directory beside its configuration file, plus what its core.profiles key names. Searched from the last to the first: the closest scope takes priority.
  • --config and -c can name directories too, for one run
  • the chips, the boards and default are built into the binary and asked last. So a project can add .aceprofiles/esp32c6.yaml and replace the one ace provides.
  • .aceprofiles is searched whether or not the project has a configuration file
